# 1주차 1day-01 — SQL Injection 분석 기록

이 폴더는 완성된 정답만 모으는 곳이 아니다. 팀원이 나중에 분석을 이어받아도 **왜 그런 결론을 내렸는지** 알 수 있도록 가설, 근거, 확인 결과를 함께 기록한다.

## 분석 순서

```text
1. GeoPandas — SQL 값 자리에 문자열을 직접 조립한 사례
        ↓
2. ormar     — ORM이 입력을 SQL 표현식으로 승격한 사례
        ↓
3. Django    — 값이 아닌 SQL 식별자(alias) 검증 사례
```

이 순서는 취약점의 심각도순이 아니라 **학생이 이해하기 쉬운 순서**다.

1. GeoPandas에서 기존 SQLi 강의의 핵심인 문자열 조립과 매개변수 바인딩을 복습한다.
2. ormar에서 ORM을 사용해도 입력이 raw SQL로 바뀌면 취약할 수 있음을 확인한다.
3. Django에서 매개변수 바인딩하기 어려운 식별자와 차단 목록 검증의 한계를 다룬다.

## 모든 후보에 적용할 공통 분석 흐름

```text
공개 정보 확인
    ↓
정상 사용법 이해
    ↓
외부 입력의 시작점(source) 찾기
    ↓
함수 호출을 따라 입력 흐름 추적
    ↓
SQL로 해석되는 지점(sink) 찾기
    ↓
생성 SQL 추정 또는 출력
    ↓
안전한 입력과 공격 입력 비교
    ↓
패치 diff와 테스트 분석
    ↓
재현 및 영향 범위 확인
    ↓
학생 눈높이로 다시 설명
```

## 기록 규칙

각 문서의 `분석 로그`에는 작업할 때마다 다음 형식으로 추가한다.

```markdown
### YYYY-MM-DD — 조사 주제 / 작성자

- 가설:
- 확인 방법:
- 확인한 사실:
- 근거: 파일·줄 번호 또는 URL
- 아직 모르는 점:
- 다음 작업:
```

중요한 구분:

- 공식 문서나 코드로 확인한 내용은 **확인됨**으로 표시한다.
- 실행하지 않고 코드만 보고 판단한 내용은 **추정**으로 표시한다.
- 블로그나 기존 후보 문서에서 가져왔지만 재확인하지 않은 내용은 **미확인**으로 표시한다.
- 핵심 보안 코드의 diff와 전체 커밋 규모를 따로 기록한다.
- PoC 성공뿐 아니라 실패한 입력과 실패 이유도 남긴다.

## 최종 블로그 글의 공통 목차

각 분석이 끝나면 조사 기록을 지우지 않고, 문서 위쪽의 본문을 다음 순서로 완성한다.

1. 이 취약점은 무엇인가
2. 정상적으로는 어떻게 사용하는가
3. 공격자가 조종할 수 있는 값은 무엇인가
4. 입력이 코드 안에서 어떻게 이동하는가
5. 어느 줄에서 SQL의 일부가 되는가
6. 정상 SQL과 공격 후 SQL은 어떻게 다른가
7. 패치는 무엇을 바꾸었는가
8. 왜 그 수정으로 막히는가
9. 재현 결과와 실제 영향
10. 기존 SQL Injection 강의와 연결되는 개념
11. 분석하면서 틀렸던 가설과 남은 질문
