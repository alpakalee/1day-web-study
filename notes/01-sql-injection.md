# 1주차 — SQL Injection

> 40분 발표 · 웹/SQL 초보자 대상  
> 목표: AI로 문제를 풀더라도, 보이지 않는 SQL의 모양을 추정하고 답이 작동하는 이유를 설명한다.

## 중심 문장

**SQL Injection은 사용자 입력이 단순한 값이 아니라 SQL 문장의 일부가 되는 문제다.**

**SQLi 풀이란 페이로드를 맞히는 일이 아니라, 보이지 않는 SQL 문장과 서버가 제공하는 관찰 신호를 추론하는 과정이다.**

```text
내 입력 ──▶ 서버가 SQL을 만듦 ──▶ DB가 실행 ──▶ 결과에 따라 화면이 바뀜
                    ▲
                    └─ 입력이 SQL의 의미를 바꾸면 SQL Injection
```

# 1. SQL이란?

웹사이트의 데이터는 보통 표와 비슷한 형태로 데이터베이스에 저장된다.

```text
users
┌────┬───────────────┬───────────────┐
│ id │ username      │ password_hash │
├────┼───────────────┼───────────────┤
│ 1  │ administrator │ ...           │
│ 2  │ alice         │ ...           │
└────┴───────────────┴───────────────┘
```

SQL은 데이터베이스에 보내는 질문이다.

```sql
SELECT * FROM users WHERE username = 'alice';
```

```text
SELECT *         모든 열을 보여 줘
FROM users       users 표에서
WHERE            다음 조건을 만족하는 행만
username='alice' username이 alice인 행
```

이번 시간에 필요한 것은 `SELECT`, `FROM`, `WHERE`, `AND`, `OR`, 문자열의 `'`, 주석 `--` 정도다.

# 2. 로그인 페이지에서 생기는 일

```text
┌──────────┐       ┌──────────┐       ┌────────────┐
│ 브라우저   │  ①    │ 웹 서버  │  ②    │ 데이터베이스 │
│ ID / PW  │ ───▶ │ SQL 생성 │ ───▶ │ 사용자 조회  │
└──────────┘       └────┬─────┘       └─────┬──────┘
                        └──── 결과 ◀─────────┘
                           로그인 성공/실패
```

사용자가 `alice`와 `1234`를 입력하면 서버는 개념적으로 이런 질문을 만든다.

```sql
SELECT * FROM users
WHERE username = 'alice' AND password = '1234';
```

브라우저가 DB에 직접 질문하는 것이 아니다. 서버가 입력을 받아 SQL을 만들며, 그 방식이 안전하지 않으면 입력값이 질문 자체를 바꾼다.

> 실제 서비스는 비밀번호 원문을 그대로 저장·비교하면 안 된다. 여기서는 구조를 보기 위해 단순화했다.

# 3. 가장 단순한 SQL Injection

정상 입력은 따옴표 안에서 하나의 값으로 머문다.

```text
username = '  +  alice  +  '
                    ↓
           username = 'alice'
```

입력이 `administrator'--`라면 경계가 달라질 수 있다.

```text
username = 'administrator'--' AND password = ''
            └──── 값 ────┘ ▲ └──── 주석 처리 ────┘
                            └ 문자열을 닫고 SQL 구조로 탈출
```

DB가 해석하는 의미는 다음에 가까워진다.

```sql
SELECT * FROM users WHERE username = 'administrator';
```

```text
공격 전: 관리자이면서 비밀번호도 맞아야 함
공격 후: 관리자이기만 하면 됨
```

문자열을 외우는 대신 세 가지를 설명한다.

1. 입력이 SQL의 어느 위치에 들어갔는가?
2. 따옴표와 주석이 무엇을 바꿨는가?
3. 조건이 바뀌어 결과가 어떻게 달라졌는가?

## 페이로드를 세 조각으로 읽기

```text
[현재 문맥 닫기] + [원하는 SQL 넣기] + [남은 문법 정리]

'                 OR 1=1              --
▲                    ▲                 ▲
문자열 닫기          조건 변경         뒤쪽 문법 주석 처리
```

공격자의 입력도 최종적으로는 **문법적으로 유효한 SQL**을 만들어야 한다.

```text
서버가 만든 틀
WHERE category = '[입력]' AND released = 1

생각하는 순서
1. 문자열·숫자·괄호 중 어떤 문맥 안에 있는가?
2. 그 문맥을 어떻게 닫는가?
3. 어떤 조건이나 조회를 추가할 것인가?
4. 서버가 뒤에 붙이는 문법을 어떻게 정리할 것인가?
```

# 4. 기본 문제

## 문제 1 — 숨겨진 상품

```sql
SELECT * FROM products
WHERE category = 'Gifts' AND released = 1;
```

```text
[Gifts인가?] ─ AND ─ [출시됐는가?]
      참                    참
                 ↓
              화면에 표시
```

- 숨겨진 상품을 막는 조건은 무엇인가?
- 그 조건이 주석이 되면 무엇이 달라지는가?
- 입력 후 완성된 SQL은 어떤 모습인가?

## 문제 2 — 로그인 우회

AI가 `administrator'--`를 답으로 주었다면 제출 전에 다음을 말한다.

```text
입력 위치  → username
닫힌 것    → username 문자열
사라진 것  → password 비교 조건
결과       → 관리자 행이 반환될 가능성
```

AI에는 다음처럼 요청한다.

```text
정답만 주지 말고 원래 SQL과 입력 후 SQL을 추정한 뒤,
각 기호가 쿼리의 의미를 어떻게 바꾸는지 설명해 줘.
```

완성된 SQL은 서버 코드를 보지 못한 상태의 **가설**일 수 있다는 점도 기억한다.

# 5. SQL Injection을 보는 세 가지 축

```text
① 입력 문맥         ② 결과 채널         ③ 현재 목표

문자열              결과가 직접 보임     취약성 확인
숫자                화면의 참/거짓 차이  조건 변경
검색어              오류 차이            인증 우회
정렬·열 이름         시간 차이            DB 구조 파악
저장 후 재사용       외부 상호작용        데이터 추출
```

새 문제를 만나면 먼저 묻는다.

1. 입력은 SQL의 어디에 들어갔는가?
2. 서버는 DB 결과를 어떤 신호로 보여 주는가?
3. 지금 단계의 목표는 무엇인가?

## 대표 기법 지도

각 기법은 완전히 별개라기보다 **DB의 결과가 어떻게 보이는가**에 따라 달라지는 접근이다.

```text
                    SQL Injection
                           │
              ┌────────────┴────────────┐
              │ 결과가 화면에 보임      │ 결과가 직접 안 보임
              ▼                         ▼
        조건 변경 / UNION              Blind SQLi
              │                    ┌─────┼─────┐
              ▼                    ▼     ▼     ▼
       다른 데이터를 붙임          화면차이 오류차이 시간차이
```

## 조건 변경

```text
원래: A AND B
변경: A OR 항상 참
```

숨겨진 데이터를 보거나 로그인 검사를 우회하는 기본 형태다.

## UNION

`UNION`은 두 조회 결과를 한 결과표로 이어 붙인다.

```text
상품 조회 결과                 사용자 조회 결과
┌────────┬────────┐           ┌────────┬────────┐
│ name   │ price  │  UNION    │ user   │ secret │
└────────┴────────┘     ▶     └────────┴────────┘
```

CTF에서 기억할 개념은 두 가지다.

- 양쪽 조회 결과의 **열 개수**가 같아야 한다.
- 대응하는 열의 **자료형**이 맞아야 한다.

그래서 “원래 결과는 몇 열인가?”, “문자열을 표시할 수 있는 열은 어디인가?”를 먼저 알아낸다.

`NULL`은 여러 자료형과 호환되기 쉬워, 아직 열의 자료형을 모를 때 자리 채우기로 자주 사용한다.

```text
열 개수 확인
    ↓
문자열을 담을 수 있는 열 확인
    ↓
실제 화면에 출력되는 열 확인
    ↓
필요한 데이터 조회
```

## 데이터베이스 식별

```text
MySQL · PostgreSQL · Oracle · SQL Server
       ↓
주석, 함수, 문자열 연결, 시간 지연 문법이 서로 다름
```

오류 메시지나 동작하는 함수를 통해 DB 종류를 추정한다. AI에게 DB 종류를 알려 주지 않으면 맞지 않는 문법을 받을 수 있다.

## Blind SQL Injection

결과가 보이지 않아도 서버 반응의 차이로 정보를 추론할 수 있다.

```text
질문: 비밀값의 첫 글자가 'm'보다 뒤인가?

참  ─▶ "Welcome back" 표시
거짓 ─▶ 표시 없음
              ↓
       한 글자씩 범위를 좁힘
```

화면이 같다면 오류 발생 여부나 응답 시간 차이를 신호로 쓰기도 한다. 여기서는 원리만 이해하고 DB별 문법은 자료와 AI의 도움을 받는다.

Blind SQLi는 데이터베이스와 **예/아니오 질문으로 대화하는 것**이라고 생각할 수 있다.

```text
첫 글자가 m보다 뒤인가? ─▶ 예
첫 글자가 t보다 뒤인가? ─▶ 아니오
첫 글자가 q보다 뒤인가? ─▶ 예
              ⋮
        범위를 좁혀 값 추론
```

한 번의 응답은 적은 정보만 주지만 질문을 반복하면 값을 복원할 수 있다. 자동화 도구도 본질적으로 이 반복을 빠르게 수행한다.

# 6. CTF·버그바운티에 도움 되는 실전 관점

## 문제 해결의 전체 흐름

```text
입력 지점 발견
      ↓
입력 문맥 추정
      ↓
취약성 확인
      ↓
DB 종류 추정
      ↓
쿼리 결과의 모양 파악
      ↓
테이블·열 구조 파악
      ↓
목표 데이터 또는 동작 확인
      ↓
실제 영향 판단
```

AI에게도 현재 단계와 이미 확인한 사실을 알려 줘야 다음 가설의 품질이 높아진다.

## 입력창만 입력 지점은 아니다

```text
URL 파라미터 · 폼 · JSON · 쿠키 · HTTP 헤더 · 저장 후 재사용되는 값
```

로그인뿐 아니라 검색, 상품 필터, 정렬, 사용자 조회 등 서버가 DB 질의에 사용하는 입력을 생각한다.

## 오류가 없다고 안전한 것은 아니다

```text
에러가 보임     → 쿼리 구조나 DB를 추정할 단서
화면이 달라짐   → 참과 거짓을 구분할 수 있음
시간만 달라짐   → Blind 가능성
아무 차이 없음  → 가설이 틀렸거나 다른 관찰 지점이 필요
```

## 테이블 이름은 처음부터 주어지지 않는다

CTF에서는 `users`, `username`, `password`가 바로 주어지기도 하지만 현실에서는 DB 구조도 찾아야 한다.

```text
일반 데이터                  DB가 가진 구조 설명서

products                    테이블 목록
users             ◀────     열 이름
orders                      자료형
```

많은 DB는 자신의 테이블과 열 구조를 설명하는 시스템 카탈로그를 제공한다. 이를 조회하거나 이름을 추정해 목표 데이터의 위치를 찾는다.

# 7. PortSwigger 치트시트에서 기억할 핵심

치트시트는 외우는 표가 아니라 **DB 종류에 맞는 문법을 찾는 사전**이다. 먼저 목적을 정하고 해당 행만 찾아본다.

```text
문자열을 합칠 것인가?  → 문자열 연결
한 글자를 비교할 것인가? → 부분 문자열
뒤쪽 문법을 없앨 것인가? → 주석
DB 종류를 확인할 것인가? → 버전 조회
테이블을 찾을 것인가?   → 시스템 카탈로그
결과가 보이지 않는가?   → 조건부 오류·시간 지연
```

## DB별 핵심 차이

| 목적 | Oracle | Microsoft SQL Server | PostgreSQL | MySQL |
|---|---|---|---|---|
| 문자열 연결 | `a \|\| b` | `a + b` | `a \|\| b` | `CONCAT(a,b)` |
| 일부 문자 추출 | `SUBSTR()` | `SUBSTRING()` | `SUBSTRING()` | `SUBSTRING()` |
| 버전 확인 | `v$version` | `@@version` | `version()` | `@@version` |
| 시간 지연 | `dbms_pipe.receive_message()` | `WAITFOR DELAY` | `pg_sleep()` | `SLEEP()` |

> 부분 문자열의 시작 위치는 이 치트시트 예시에서 1부터 센다. Blind SQLi로 한 글자씩 비교할 때 자주 놓치는 부분이다.

## 주석은 공통처럼 보여도 다르다

```text
Oracle       --comment
Microsoft    --comment 또는 /* comment */
PostgreSQL   --comment 또는 /* comment */
MySQL        #comment, /* comment */, -- comment
```

MySQL의 `--` 뒤에는 공백이 필요하다. 같은 페이로드가 DB에 따라 실패하는 대표적인 이유다.

## DB 구조 찾기

```text
Microsoft · PostgreSQL · MySQL
information_schema.tables   → 테이블 목록
information_schema.columns  → 열 목록

Oracle
all_tables                   → 테이블 목록
all_tab_columns              → 열 목록
```

```text
DB 종류 확인 → 테이블 목록 → 관심 테이블의 열 목록 → 목표 데이터
```

## Blind 상황의 신호 선택

```text
결과가 보임       → UNION 등으로 직접 확인
참/거짓 차이      → 조건부 응답
오류 차이         → 조건부 오류
시간 차이         → 조건부 시간 지연
응답과 무관함     → OAST 같은 외부 상호작용 개념
```

Stacked query는 세미콜론 뒤에 별도 쿼리를 실행하는 개념이지만 DB와 애플리케이션 API의 지원 여부에 크게 좌우된다. 특히 Oracle은 지원하지 않으며, MySQL도 일반적으로 제한된다. “SQLi가 있다 = 여러 쿼리를 마음대로 실행할 수 있다”는 뜻이 아니다.

필터 우회에서는 대소문자 변경이나 주석을 공백처럼 쓰는 방식이 존재한다. 이것은 차단 목록이 SQL 문법 전체를 안전하게 이해하지 못한다는 사례이며, 방어의 결론은 필터 경쟁이 아니라 매개변수화다.

> 상세 DB별 표현식은 필요할 때 [PortSwigger SQL injection cheat sheet](https://portswigger.net/web-security/sql-injection/cheat-sheet)에서 확인한다.

# 8. Prepared Statement

```text
취약한 방식
SQL 앞부분 + 사용자 입력 + SQL 뒷부분
                 └─ 값과 명령의 경계가 무너질 수 있음

안전한 방식
SQL 구조: SELECT ... WHERE username = ?
입력값:   administrator'--
                 └─ 서로 분리해서 DB에 전달
```

Prepared Statement는 SQL 구조를 먼저 정하고 사용자 입력을 별도의 값으로 전달한다. 입력에 SQL처럼 보이는 문자가 있어도 문장 구조가 아니라 데이터로 처리된다.

기억할 점:

- 작은따옴표를 삭제하는 것만으로 해결되지 않는다.
- 값이 들어가는 자리에는 매개변수화를 사용한다.
- 테이블명이나 정렬 방향처럼 값으로 처리하기 어려운 부분은 허용 목록 등이 필요하다.
- AI가 작성한 코드도 사용자 입력을 SQL 문자열에 연결하는지 확인한다.

# 9. 마무리 문제

## 문제 3

참인 조건에는 `Welcome back`이 보이고 거짓인 조건에는 사라진다. DB 조회 결과 자체는 보이지 않는다.

정답: 응답 차이를 사용하는 Blind SQL Injection을 생각할 수 있다.

## 문제 4

`UNION`으로 다른 조회 결과를 붙이기 전에 무엇을 알아야 하는가?

정답: 원래 결과의 열 개수와 값을 표시할 수 있는 열의 자료형.

## 문제 5

AI: “작은따옴표를 차단하면 SQL Injection은 해결된다.”

문제점: SQLi는 문자열 외의 문맥에서도 생기며 차단 목록은 우회나 누락이 생길 수 있다. 기본 해결은 SQL 구조와 값을 분리하는 매개변수화다.

## 문제 6 — 페이로드를 해체하라

```text
' OR 1=1--
```

정답:

```text
'       현재 문자열 문맥을 닫음
OR 1=1 조건을 항상 참으로 바꿈
--      서버가 뒤에 붙이는 문법을 주석 처리
```

## 문제 7 — 지금 어느 단계인가?

열 개수는 알아냈지만 어느 열에 문자열을 표시할 수 있는지 모른다. 다음 목표는 무엇인가?

정답: 각 열의 자료형과 화면에 출력되는 위치를 확인하는 것.

# 자주 생기는 오해

| 오해 | 실제 |
|---|---|
| SQLi는 로그인 폼에서만 생긴다. | DB 질의에 쓰이는 다양한 입력에서 생길 수 있다. |
| 오류가 없으면 안전하다. | 화면·오류·시간 등 다른 차이가 신호가 될 수 있다. |
| ORM을 쓰면 무조건 안전하다. | Raw query나 문자열 조립을 사용하면 취약할 수 있다. |
| 특수문자를 막으면 해결된다. | 문맥이 다양하고 우회 가능성이 있어 매개변수화가 기본이다. |
| WAF가 SQLi를 해결한다. | 공격을 어렵게 할 뿐 취약한 쿼리 생성을 고치지는 않는다. |
| 하나의 페이로드가 모든 DB에서 통한다. | DB 종류와 입력 문맥에 따라 문법이 달라진다. |
| Prepared Statement가 모든 동적 SQL을 해결한다. | 열 이름·정렬 방향 등에는 허용 목록 같은 별도 설계가 필요하다. |
